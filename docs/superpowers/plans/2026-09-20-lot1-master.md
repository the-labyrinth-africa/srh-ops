# Lot 1 — Finition Phase 2 et fuites d'accès : feuille de route

> **For agentic workers:** ce document est la feuille de route du Lot 1. Il ne s'exécute pas tel quel : chaque sous-lot a son propre plan détaillé. Le sous-lot 1A est prêt à exécuter (`2026-09-20-lot1a-acces-et-mot-de-passe.md`) ; 1B et 1C sont décrits ici au niveau tâche et recevront leur plan détaillé quand leurs décisions d'infrastructure seront prises (section 3).

**Goal:** Rendre la Phase 2 (terrain) utilisable en production : plus aucune fuite d'accès entre rôles, réinitialisation de mot de passe et rapports envoyés par e-mail, photos hors de la base de données, PWA fiable.

**Spec:** `docs/proposition-digitalisation.pdf` §6 (mobile), §7 (rapport), §14 (notifications) ; plan d'alignement `2026-09-19-alignement-proposition-digitalisation.md` (Lot 1, tâches 1.1 à 1.6) ; journal des revues du Lot 0 (défauts consignés, section 1).

**Tech Stack:** Next.js 16, React 19, Mongoose, NextAuth v4 (JWT), Zod, Vitest + mongodb-memory-server + fake-indexeddb. Ajouts prévus : stockage objet (1C), transport e-mail (1B).

## Global Constraints

- Le client s'appelle **SRH**. Interface et libellés en français. Statuts exacts : `Planifiée → Affectée → En route → En cours → Terminée → Rapportée` (+ `Retardée`, `Annulée`).
- Rôles : `admin`, `dispatcher`, `lecture`, `chauffeur`, `client`. Aucun compte `client` réel avant la fin du sous-lot 1A.
- Aucun secret, identifiant de base de données ou donnée client réelle dans Git ; `.env.local` reste ignoré. Ne jamais lancer `npm run build`, `npm run seed` ou `scripts/seed-admin.ts` sans `--on-build` contre la base réelle.
- Aucun mot de passe, jeton ou corps d'e-mail dans les logs.
- Une quantité collectée de 0 n'est pas une collecte valide.
- Chaque sous-lot se termine par : `npx tsc --noEmit`, `npm run lint` (0 erreur), `npx vitest run` (tout vert), puis revue de branche complète.
- Les services externes (stockage, e-mail) se provisionnent par le Marketplace Vercel (`vercel integration …`), jamais avec un SDK codé à la main ni un simulacre laissé en production.

## 2. Ordre d'exécution

```
1A (accès + mot de passe)  ──►  1B (e-mail, reset, rapport envoyé)  ──►  1C (photos objet + PWA)
     sans dépendance externe          dépend du transport e-mail            dépend du stockage objet
```

- **1A d'abord** : il ferme les fuites de sécurité, ne dépend d'aucun service externe et débloque la création de comptes `client`.
- **1B avant 1C** : 1B fournit le transport d'e-mail et la réinitialisation à jeton ; 1C en a besoin pour l'envoi du rapport au client (tâche 1C.8), qui embarque les photos et doit donc être écrite une seule fois sur l'API de stockage définitive.
- **1C** finit la PWA : la variable `NEXT_PUBLIC_ENABLE_PWA` ne passe à `true` en production qu'après la recette manuelle de 1C.

Durée indicative : 1A ≈ 4 j, 1B ≈ 3 j, 1C ≈ 6 j (dont recette terrain).
